# 仕様書レビュー規約 (Devin Review 用)

本ファイルは Devin Review の指示ファイルです。`docs/` 配下のうち **コードベースから生成した仕様書** の変更 PR をレビューするときの観点を定義します。

## 適用範囲 (厳守)
- 対象: `docs/*_spec.md` と、同名の `docs/*_spec.pdf` (仕様書本体。`!spec_pdf` / `!spec_update` プレイブックで生成・更新されるもの)
- 対象外 (本規約を適用しない。通常のレビューのみ行う):
  - `docs/` 配下の上記以外のドキュメント (業務要件定義書、画面台帳 `*_screen_ledger.md`、トレーサビリティ `*_traceability.md`、テストレポート、README、議事録、ADR など)
  - ソースコード・テスト・ビルド設定・CI 設定など `docs/` 以外のすべての変更 (通常のコードレビューを行う。本規約の観点は持ち込まない)
- PR に仕様書とコードの両方が含まれる場合は、仕様書ファイルにだけ本規約を適用し、コードは通常どおりレビューする。

---

## 1. フロントマター (必須)
仕様書冒頭の YAML front matter に以下のキーが揃っていること。欠落は指摘する。

```yaml
---
title: <システム名> 仕様書
ref: <対象リポジトリの ref (ブランチ名またはコミット SHA)>
generated: YYYY-MM-DD
evidence: <根拠の種別。例: ソースコード + 実機確認 / ソースコードのみ>
---
```

- **R1-1**: `ref` が PR の HEAD (または直近のコード変更を含むコミット) を指していること。古い ref のまま本文だけ変わっている場合は指摘。
- **R1-2**: 本文に実質的変更があるのに `generated` が更新されていない場合は指摘。
- **R1-3**: `evidence` に実機確認の有無が明記されていること。実機確認していない項目を「確認済み」のように書いていないこと。

## 2. 章立て (必須セクション)
以下の 9 節をこの順で含むこと。欠落・順序違反は指摘 (節番号の表記ゆれは許容)。

1. 概要・対象範囲・前提
2. 機能一覧 (機能 ID / 名称 / 入口 / 主要ソース の表)
3. 画面 (または API) フロー
4. データモデル
5. 業務ルール
6. 機能仕様詳細
7. メッセージ一覧
8. 移行・実装時に保持すべき要素
9. 対象外・既知の問題・前提・自己判断事項

- **R2-1**: 必須節の欠落。
- **R2-2**: 「5. 業務ルール」の各項に根拠 (ファイル / プログラム / 関数・サブルーチン名) が無い。
- **R2-3**: 「9. 対象外・既知の問題・前提・自己判断事項」が空、または対象外機能が機能一覧から消えている (対象外は「対象外 (言及のみ)」として一覧に残す)。
- **R2-4**: 更新 PR (既存仕様書の変更) で末尾の「改訂履歴」表に「日付 / 対象 PR 番号 / 変更概要」の行が追加されていない。

## 3. 根拠とトレーサビリティ
- **R3-1**: 機能一覧の各機能 ID が「6. 機能仕様詳細」に対応ブロックを持つこと (逆方向も同様)。孤立 ID は指摘。
- **R3-2**: 業務ルール・機能詳細・メッセージの記述に、ソース上の位置 (ファイル名 / プログラム名 / 関数名) が付いていること。「DeepWiki によれば」「PR 説明によれば」など二次情報だけを根拠にした記述は指摘。
- **R3-3**: 推測・未確認の記述は「要確認」と明示されていること。断定形で書かれた推測は指摘。
- **R3-4**: コメントと実装が食い違う旨の注記がある場合、「実装 (と実データ) を正とする」方針で書かれていること。
- **R3-5**: 画面タイトル文言・エラー文言・メッセージ ID・テーブル名・列名など、ソースからそのまま引用すべき固有名がソースと一致していること (PR の差分から確認できる範囲で)。

## 4. 差分更新 PR の観点 (`!spec_update` が作成する `[spec-update]` PR)
- **R4-1**: 変更のない節が書き換えられていない (既存の機能 ID・節構成・表形式・文体が維持されている)。全面書き直しは指摘。
- **R4-2**: 対象 PR のコード変更で振る舞いが変わった箇所 (入力順、検証ルール、DB 読み書き、遷移、エラー文言、保持要素) が仕様書に反映されているか。PR 本文「やったこと」に列挙された機能 ID と実際の差分が一致しているか。
- **R4-3**: リファクタ・コメント変更のみで振る舞いが変わらない変更が仕様として書かれていないか。
- **R4-4**: 削除された機能・テーブル・メッセージへの参照が仕様書に残っていないか。

## 5. 分量と体裁
- **R5-1**: `*_spec.md` が変更されているのに同名 `*_spec.pdf` が更新されていない (または逆)。両方が同じ PR に含まれること。
- **R5-2**: PR 本文「テスト」欄に PDF のページ数が記載され、8〜12 ページの範囲内であること。範囲外は指摘。
- **R5-3**: 表の途中改ページや見出しだけがページ末に残る等の PDF 体裁は、PR 本文に目視確認の記載があればよい (PDF 自体の内容審査はしない)。
- **R5-4**: 用語・表記ゆれ (例: 「ユーザー」と「ユーザ」、「展示 ID」と「展示ID」) の混在。
- **R5-5**: 本文に未解決の TODO / FIXME / `???` が残っている (残す場合は「9. 対象外・既知の問題・前提・自己判断事項」へ)。

## 6. セキュリティ
- **R6-1**: 認証情報・接続シークレットの値 (パスワード、トークン、鍵) が本文・表・コードブロックに含まれている場合は必須指摘。ホスト名・ライブラリ名・環境変数名のみの記載は許容。
- **R6-2**: 個人情報 (実在の氏名・メール・バッジ番号など) が実データとして貼り込まれていないか。サンプルは架空値であること。

---

## レビュー出力の形式 (Devin への指示)
- 指摘・所見・分析はすべて **日本語** で記述する。
- 指摘は重大度 (🔴必須 / 🟡推奨 / 🔵任意) とルール ID 付きで列挙する。フロントマター欠落 (R1)・根拠なし記述 (R3-2, R3-3)・シークレット露出 (R6-1)・MD と PDF の不一致 (R5-1) は 🔴、章立て順序・改訂履歴・分量は 🟡、表記ゆれ・体裁は 🔵 とする。
- 問題が無い節は「OK」と明記し、過剰な指摘は避ける。
- 本規約の対象外ファイルに対して本規約のルール ID を付けた指摘をしない。

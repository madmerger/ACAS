# Legacy ACAS oracle (W0-3)

This is an executable baseline for later Java comparisons, not a replacement for
ACAS or a general-purpose ISAM migration tool. It builds the unmodified legacy
application, generates real indexed/relative files from a text fixture, drives
the real SL070 terminal with pexpect, and exports the observed data and report.

## Run

On Ubuntu install `gnucobol` (3.x; `cobc -info` should show the BDB indexed file
handler), Python 3.12, then:

```sh
python3 -m pip install -r tools/oracle/requirements.txt
python3 tools/oracle/runner.py --compare
python3 -m pytest -q tools/oracle/tests
```

The runner invokes the existing `./comp-all.sh` in a copy of tracked sources,
not in the checkout. No SQL/DAL flavour is used. Each invocation has a unique
build directory, each case a fresh working directory under `results/`; use
`--output /absolute/path` to put all artifacts elsewhere. Reruns never reuse
data. Outputs and build artifacts are ignored by git. Delete old result
directories yourself when no longer needed. CI uploads them even on failure.
Legacy compilation scripts do not propagate every compiler failure, so the
runner also rejects compiler `error:` diagnostics in `build.log`.

`results/SL-ANALYSIS-001.json` contains sorted-key canonical JSON. `--compare`
compares against `golden/<id>.json`, prints a unified diff, and exits nonzero
on mismatch. Missing files, invalid cases, terminal timeouts and unsuccessful
processes fail the run; inspect `build.log` and `<id>-*/terminal.log`.
There is deliberately no automatic golden-update switch: inspect the actual
JSON and raw artifacts before copying measured results to a golden file.

## Baseline and adapter boundary

`fixture.json` is the shared portable source of supplier and purchase/sales
analysis records, including valid supplier `SUP0001` and P/S code `a1` for
future stock validation scenarios (ST101/ST110/ST111). It contains no ISAM
binaries and is usable by a Java test loader. `bridge.cbl` uses the repository's
original copybooks to generate `system.dat` (relative, record 1), `analysis.dat`
and `purchled.dat` (indexed) afresh. Configuration is minimal and deterministic:
Oracle Company, flat files, date 2 January 2020, international date display.
It is a prepared fixture, **not a test of first-run system setup**.

The adapter calls `sl070` with the same linkage as the Sales menu's L entry;
it skips authentication/top-level menus. Importantly it compiles against
**sales/wsnames.cob**, not the differently shaped common/global file tables.
No production COBOL sources or build scripts are modified. Extend the adapter
and schema explicitly to support other programs; arbitrary executable paths
and shell commands are not accepted from cases.

After terminal exit the adapter reads the real files using COBOL `READ NEXT`:
the COBOL runtime handles BDB indexes, binary numbers and packed decimals.
It exports delimited text, then Python produces JSON. Analysis records include
all fields; suppliers currently export the code/name projection only, not
balances or all purchase-ledger fields. Other files/modules are not yet
decoded. Add a copybook-based exporter before adding cases that touch them.
Empty files yield empty arrays and malformed export rows fail conversion.

The isolated `lpr` shim preserves `prt-1` instead of contacting a real printer
or deleting the file. The report is generated by legacy SL070, not the shim.
Python extracts fixed-column records plus normalized report lines. Printed
G/L numbers are the **observed** values (SL070 divides by 100 outside IRS),
not the raw stored values. Group ledger labels are not invented for detail
rows when the original report leaves them blank. Dates are replaced with
`<DATE>` in report/screen JSON; raw reports/transcripts remain untouched.

## Shared cases contract

`cases.schema.json` (JSON Schema 2020-12) validates `cases.json`. Version 1:

* `id`: unique safe filename; `description`: human-readable purpose.
* `program`: legacy dispatch identity (currently `sl070` only).
* `menu_path`: logical navigation for humans/future Java adapters; the terminal
  adapter enters at `program`, not at the first top-level menu.
* `input`: implementation-neutral business values for Java comparison drivers.
* `steps`: ordered literal `expect` text and `send` keystrokes; JSON `\r` means
  Enter. No regex/shell syntax. Optional `capture` names a screen snapshot
  taken after the expectation and before sending. Terminal metadata may be
  ignored by Java adapters, which should drive `input` through their own API.
* `outputs.data`: named structured datasets (currently analysis and suppliers).
  `outputs.reports`: printer outputs to decode (currently `prt-1`).

The sample creates sales analysis group `b` through maintenance option 1,
prints all P/S records with option 4, captures the returned menu, and exits
with option 9. Its golden is measured from the legacy run: five analysis
records, one supplier, and five printed records, including the created group.
Every case gets the same baseline independently; ordering cases must not
affect results. Add new cases/goldens as migration features are implemented.

Raw terminal transcripts are retained and pyte reconstructs the captured
80x24 screen using TERM=vt100 (avoids unsupported xterm repeat-character
sequences). These are machine captures, not a browser recording or a visual
assertion of the entire application. The oracle workflow is the aggregate
check for this Python/COBOL tooling; no lint/typecheck scripts exist here.
